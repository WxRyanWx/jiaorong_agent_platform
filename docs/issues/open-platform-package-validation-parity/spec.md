# 开放平台技能 / 连接器包校验统一（spec）

状态：active
最后确认：2026-11-25

## 背景

开放平台「技能 / 连接器」上传分两步：**创建草稿**只在客户端解析包元信息（`parseSkillPackage` /
`parseConnectorPackage`），**确认发布**把 zip 透传给服务端 `/assets/publish` 复验。

线上反馈暴露出两条路径口径不一致，且客户端一侧明显偏弱：

- 包内路径用 Windows 反斜杠时，客户端报「技能 zip 根目录必须包含 SKILL.md」，与真实原因不符。
- `name` 不符合命名规则、路径含 `..` 或绝对路径时，客户端一律放行，用户点到「确认发布」才失败。
- 非 zip / 截断包直接抛出 fflate 英文原文 `invalid zip data`。
- 客户端错误文案硬编码，未走 i18n；`t('routes.openPlatformPackageInvalid')` 是死代码。

后端在发布时的额外校验（如 GBK 文件名、反斜杠等）本次不处理，仍由服务端兜底。

## 用户需求

1. **前端的上传校验与发布校验规则统一**：同一份 zip 在「选包」阶段就能得到与发布阶段一致的前端判定。
2. 校验失败时给出**准确、可操作**的中文提示，并指出具体是哪个条目、什么原因。
3. 技能与连接器两条链路使用同一套包校验规则。

## 目标

- 抽出共享的包校验模块，技能 / 连接器解析器共用。
- 客户端在创建草稿阶段即执行：zip 可解析、条目路径安全、根标记文件存在、name 合法。
- 错误文案走 i18n，按地区语言输出。

## 验收标准

- 含反斜杠条目的包 → 报「包内路径不允许包含反斜杠，请用标准压缩工具重新打包并给出首个违规条目名」，**不再**报「缺少 SKILL.md」。
- `../x`、`/abs`、含控制字符的条目 → 分别报对应的路径安全问题，并在文案中带出该条目名。
- `name` 不匹配 `/^[a-z0-9][a-z0-9._-]*$/` 或长度超限 → 在创建阶段即报「技能 name 不符合命名规则」并给出实际值。
- 非 zip / 截断 / 空文件 → 报「包解析失败，请检查文件是否为有效 zip」，不出现 fflate 英文原文。
- 小写 `skill.md` / `mcp.json` 大小写变体 → 归一化后正常识别（与 `installLocalSkill` 既有兼容策略一致）。
- 仅子目录存在 `SKILL.md` → 报「SKILL.md 必须位于 zip 根目录」，并带出实际路径。
- 连接器解析器同样执行路径安全校验与 id 合法性校验。
- 既有正常包（`name` 合法、无异常路径）行为不变，现有测试全部通过。

## 约束

- 代码全部落在 `src/jiaorong_src/open-platform`，不新增主仓触点。
- 复用 `src/main/skill/index.ts` 已确立的 `SKILL_NAME_PATTERN`（`/^[a-z0-9][a-z0-9._-]*$/`），保持全仓单一真源口径。
- 不改变服务端契约与请求形状；仅加强客户端预检。
- 文案走 i18n（`routes.*`），补齐 zh-CN / en-US 至少两种语言。

## 非目标

- **不处理服务端校验**（GBK 文件名、后端「结构损坏」文案等），仍由后端兜底。
- 不自动改写用户包内容（反斜杠只在判定时归一化用于识别，不回写 zip）。
- 不做包大小、条目数量上限策略调整（沿用 200MB 上限）。
- 不改发布弹窗交互与版本校验逻辑。
